## 0. 先闭合 blocker：生产 FP 路径的"隧穿"（t86-F1）

`src/interaction/walk-solver.js` 与内核侧同构缺陷：移动循环**只对终点测阻挡**（一跳跨过整栋建筑），
且本地 `blocks()` **缺 `y0` 下界与门洞轴线语义**。按内核 t86 的同构修法修复：

| 项 | 修法 |
| --- | --- |
| 子步进防隧穿 | `distance` 拆为 `ceil(distance / min(radius, maxStepHeight))` 子步，**逐子步**判阻挡；被挡且无法滑动即就地停住并记录原因 |
| 口径统一 | 删除本地"简易阻挡判定"，**委托谓词层** `obstacleBlocksPoint`（与 core 求解器唯一真相源同源）；水面保留 g 侧已登记的有意口径（仅桥面可通行） |
| `blocked` 去重 | 子步进会反复命中同一障碍 → 只记去重原因（上限 8，与 core 一致） |

**实测（真实数据，断言 E12）**

| 指标 | 旧实现（只测终点，E12 内对照复刻） | 修复后 |
| --- | --- | --- |
| 从宫墙西侧 `(-300, -430)` 向东一步 30m | 终点落在墙外 ⇒ **放行 30.00m、`blocked=[]`（隧穿整道宫墙）** | **位移 0.00m**、`blocked=["OB-WALL-CITY-west"]`（停在墙前并点名） |
| 与 core 求解器一致性 | 非水面处 **411 例不一致**（t86 实测） | 短步进（0.25/1m）**32 点逐值一致**；长步进（6/30m）落点 ≤0.5m 且**首因类别与障碍身份一致** 32 点 |
| `node tests/interaction.test.mjs` | 55/56（E7 报 411 例） | **62/62**（E7 恢复，且新增 E12 的等价性采样） |

未放宽任何判据：台阶阈值、门洞语义、包络、玩家体积全部原值；E7 这把"跨求解器尺子"未删未弱化（本卡还把它扩到长步进）。

### ④ 因 `y0`/台阶阈值造成"能上不能下"的单向高差：**42 条有向边**（阈值窗口 `(0.5, 0.6]m`）

- 样例（cell=2m）：`(-10,-534)→(-8,-534)` 落差 0.541m、「能下不能上」；`(8,-534)→(10,-534)` 落差 0.541m、「能上不能下」；`(-10,-532)→(-8,-532)` 0.588m；`(238,-334)→(238,-332)` 0.600m（E 区）；
- 这些边**没有**造成孤立格（① = 0）：每一处都有其它回程路线；
- 处理：不删边、不改阈值（属"不得放宽既有判据"）。守卫按"**目标格不可返回**"判定，故当前 0 拒绝（不误伤）；未来若某条边切断回程，守卫立刻拒绝进入并在 `stats().refusals` 计数。

## 3. 修复：单向陷阱守卫（"宁可禁入"）+ 合成构造验证

- **实现**：`solver.setTraversalGuard(traversal.guardStep)` → 每次子步进在**障碍判定之后**再问守卫；目标格若"不可返回"则拒绝（原因 `oneWayTrap`）。
  容差：目标格及其 3×3 邻域内**只要有一个主分量格**就放行（避免粗栅格误伤真实通道）；
- **合成构造（E14）**：A 台地 `y=1.1`（起点分量）+ 死口袋 P `y=0.55`（只能从 A 落下、爬不回）：

| 指标 | 无守卫（旧路径） | 装守卫后 |
| --- | --- | --- |
| 朝口袋走 15m | 走到 `x=10.00`（`blocked` 无 `oneWayTrap`） | **停在 `x=0.49`**、`blocked=["oneWayTrap"]` |
| 从口袋往回走 15m | **回不来**（停在 x≈0，仍在 P，爬不上 A） | 不会陷入（根本进不去深处） |

审计在合成世界上报 **1 块 / 800 格**死口袋（中心 `(9.5,-0.5)`）⇒ 审计器确实能查出该类构造，不是空转。

## 4. 防卡死兜底（"连续受阻 N 秒 → 提示 + 一键回到最近安全点"）

- 判据（我的层可观测）：**有位移意图（`distance > 0`）却实得位移 ≈ 0**，连续累计 **1.5s**（`STUCK_SECONDS`）→ 提示 + HUD 条；
  时间由**唯一循环的 `dt`** 累加（不用挂钟），故可注入、可复现；
- HUD：`data-ui-panel="stuck"` 条（红边、文案「好像卡住了」+「连续 Ns 走不动」）+ 按钮 `data-ui-part="escape"`「回到最近安全点（G）」；`?ui=0&shot=1` 下整层隐藏（§11.3）；
- 脱困（`interaction.escapeToSafePoint` / 按钮 / **G 键**同一实现）：**只用 §7.2 请求事件**（退出 FP → 重新进入 FP），由 core 的 `nearestFpSpawn(position)` 放到**最近的已登记出生点**——出生点在 registry 契约校验内（可行走面 + 眼高），因此"不穿墙、不落水面/障碍内/包络外"由数据契约保证，本函数再逐项复核；
- **禁止随机传送**：无随机数；同一卡死点三次（按钮 / G 键 / API）落点**逐值一致**；
- 实测（E15，真实数据）：受阻累计 **2.5s** → HUD 条出现；脱困**位移 236.5m**、落点**可站立 ✓ / 包络内 ✓ / 眼高 = 可行走面+1.65 ✓ / `lastEscape.safe=true`**；5 个 fp-spawn 全部落在主分量（E16 断言）；
- 未用"放宽阻挡"或"随机传送"掩盖任何陷阱。

## 6. 量化交回（不越界改；请主理人派单）

1. **10 座亭的"空气墙"**：数据侧语义是"不可进入的整体阻挡"（`blocks:'all'`、无门洞），与"四面开敞"的视觉语义冲突。

### 9.3 ② 卡死 HUD —— **不通过（真实路径上永远不会出现）** finding **t99-F1（blocker）**

- 行为实测：玩家被顶在亭足迹边缘 **z=−377.647 恒定不动**，从 t≈2500ms 持续到 t≈8556ms（**8.56s**，= **5.7×** 判据 `STUCK_SECONDS=1.5s`），全程按住 W（有位移意图）。

- **机制级根因（可静态复验）**：`src/interaction/index.js:613` 调 `solver.noteStuckTick(dt)`，而 `noteStuckTick`（`src/interaction/walk-solver.js:522-527`）的输入 `stuck.lastDistance/lastMoved` **只由 `walk-solver.move()` 写入**；全仓 **没有任何调用点调用该 move**（`grep -rn "\.move(" src/interaction/*.js src/core/camera.js` → 0 命中；真实第一人称移动由 `src/core/camera.js` 自带的 `createFpSolver()` 承担，见 `camera.js:694`）。

- **最小修法（core/interaction，二选一）**：① 让卡死检测读**真实移动路径**：在 `tick()` 内用 `rig` 的输入态判"意图"、用 `rig.position` 的逐帧增量判"实得位移"，再调用 `noteStuckTick(dt, { intent, moved })`（该函数加两个可选入参）；② 由 `main.js` 把 camera 的 `createFpSolver()`/受阻遥测注入 interaction（与 t86/t87 已统一的"两套求解器口径"同源问题），使 `walk-solver.move()` 成为真实移动入口。
- 连带影响：`traversal.warmupStep()` 也在同一个 `tick()` 里推进 ⇒ 若 tick 链路的输入恒为 0，**单向陷阱守卫的进入条件**同样需要复核（`stats.traversalGuarded` 未在本卡读取，见 §9.6 未验证项）。

### 9.4 ③/④ `G` 脱困 —— **不通过（落点不是出生点；玩家被抛出第一人称）** finding **t99-F2（blocker）**

- 原始读数：脱困前 `mode=fp, isFp=true, (−58, 1.65, −377.647)` → 按 `KeyG` 后 `mode=oblique, isFp=false, (0, 520, −1180)`；**期望**为 `core nearestFpSpawn` 的最近登记出生点 **`VP-B-fp-spawn` (−30, 1.65, −360)**（Node 侧按 5 个 fp-spawn 复算，距离 31.49m 最近）。

  | 落点 == `nearestFpSpawn` | (−30, 1.65, −360) | (0, 520, −1180) | **✗** |

## 16. t156：`connected()` ↔ `path()` 库级口径对齐（F11）+ 过渡带双向审计（F12）

### 16.1 根因（F11）

`src/interaction/walk-graph.js` 的 `connected()` 与 `path()` 对**同一概念**给出不同答案，二重原因：
1. **整集守卫**：`const anchors = points.map(nearestCell).filter(Boolean); if (anchors.length !== points.length) return { ok:false, reason:'部分点不在可行走栅格上' }` ⇒ 只要有**任一点**取不到最近格，**整次调用即 `ok:false` 且 `unreachable` 为空** —— 一次性传 74/94 点时会把"个别点取不到格"误报成"整组不连通"（t77 的 4 点假红）；
2. `path()` 的判定是「`flood(起点)` + 终点 `parents[idx] !== -2`」，与旧 `connected` 的语义不同 ⇒ 同一概念两种实现。

### 16.2 修法（判据强度不变）

- `connected()` 改为与 `path()` **同一 `flood` 入口 + 逐点 `parents[idx] !== -2`**；取不到格 / 不同分量**逐点**记入 `unreachable`（`noCell` / `differentComponent`）——**任一不可达仍 `ok:false`**（强度不变，且不再吞掉原因）。
- `path()` 改为复用 `labelAll({x,z})`（**按锚点缓存**的同一次 flood）⇒ 同一锚点下 parents 逐值相同 ⇒ 结果**逐值不变**，同时把"每对点两次全图 flood"降为"每锚点一次"（这也是 `t148` 的性能目标）。

## 17.1 结论（一句话）
