## 2. kit 侧改了什么（最小改动，且是"物理正确"而非糊弄）

| 位置 | 改动 |
| --- | --- |
| `src/kit/geometry.js` | 前立面墙改为**"切点网格 + 洞"**生成：`openings = [门洞(整高), 各开间隔扇窗洞]`，切点取 `x/y` 极值后逐单元判定是否落在洞内；落在洞内的单元不砌墙。**同一份窗矩形（winRects）既挖洞、也生成窗扇**，故洞口与窗扇严丝合缝。墙外表面平面（`z = −halfD + inset`）与墙厚不变 |
| `src/kit/buildings.js` | 新增 `NON_CASTING_PARTS = ['window']`：隔扇窗按"裱纸/棂条窗"**不投影**（`castShadow = false`），天光可穿过洞口；`receiveShadow` 不变。另：`window` 的几何、材质（`timberLacquer`）、位置与尺寸**逐位未变** |
| 未做的事（有意） | 未给窗/任何构件加 emissive、未改任何 config 令牌、未改外立面几何、未在 roof/ceiling 上开洞（会改变外形）、未加区域/核心代码 |

**"不是自发光糊弄"的机器证据**（`tests/kit.test.mjs` §18）：窗扇材质 `emissive === #000000`；窗扇 `castShadow === false` 而墙体/屋面 `castShadow === true`。

**为什么 Δ≈0（物理原因，可复核）**：
1. **进深**：`goldenHour` 太阳仰角 ≈ 44°（方向 y 0.62 / 水平 0.79），穿过 4m 高窗带后水平射程仅 ≈ 4/0.96 ≈ 4.2m；`sunset` 仰角 ≈ 21° → ≈ 10.5m。而两个内景机位的**可见内容在开洞后方 10–30m**（B 相机 z=−128、南立面 z≈−134；C 相机 z=157、南立面 z≈149），直射光落点正好在相机附近/身后。
2. **无 GI**：three.js 只有 1 盏方向光 + ambient + hemisphere（均不遮挡），没有光反弹，室内深处只能吃 ambient/hemi。
3. **金砖基色**：`COLORS.interiorBrick = #1a1917`（线性反照率 ≈ 0.0102）。ambient 0.42 + hemi 0.5 时地板线性照度 ≈ 0.006 → ACES 后 sRGB luma ≈ 0.03–0.05，**低于 0.08 判据**；只有直射阳光（≈0.02 线性 → luma ≈0.15）才能把地板抬过阈值。
4. 因此：**所有"开洞类"手段（含门洞、窗洞、檐廊）都只能照亮洞口附近 4–10m，无法照亮取景内容**。

## 3. 量化边界：还差多少 / 什么手段有效（全部用 `?env=` 进程内覆盖实测，**未改 shared**）

（`?env=` 是 `src/main.js` 的诊断通道：只改本进程内环境预设副本，绝不写回 `config.js`）

### 3.1 ambient（环境光强度）——**不推荐**
`--view=interior --zone=B --preset=golden --env=ambient=<x>`：

| ambient | 内容均值 | 内容暗区 |
| --- | --- | --- |
| 0.42（现值） | 0.1097 | 66.03% |
| 1.0 | 0.1228 | 59.61% |
| 1.6 | 0.1343 | 50.56% |
| 2.4 | 0.1482 | **41.07%** |

外推：斜率约 −12.5pp / +1.0 ambient → 要 ≤30% 需 **ambient ≈ 3.3（约 8×）**。
副作用：全城/近景类判据是"内容暗区 ≤15% 且均值 ≥0.1"，8× ambient 会让外景整体发灰/失去阴影层次（本任务无权改 config，也未改）。

### 3.2 宫灯（`lampIntensityScale`）——**方向对，但仍不够**
（`LIGHTING.presets.goldenHour.lampIntensityScale = 0.0`、`sunset = 0.35`、`moonlitNight = 1.0`；宫灯 `intensity 18 / distance 60 / decay 1` 为 t26 已调值）

| 机位 | kit 后 | +scale 0.6 | +scale 1.0（= 夜景强度） |
| --- | --- | --- | --- |
| 金銮殿 golden | 65.93% | 54.49% | **48.72%** |
| 寝殿 dusk | 53.17% | 48.72% | **44.61%** |

即：**把日景宫灯拉到与夜景同强度也只有 ≈45–49% 暗区，仍 >30%**；且夜景本身对金銮殿有效（1.36%）而**寝殿即使夜景也 40.82%**（t26 同值 40.77%）。

### 3.3 结论：kit 侧已达上限
- kit 侧可用手段（真实洞口 + 透光窗扇 + 不投影遮蔽口径）**已全部用上**，实测 Δ≈0；
- 剩下的差距必须由 **config/环境侧**补，且不能只靠 ambient（见 3.1）；
- 需要的主判据改动是"**只作用于内景的照明/材质**"，而非全局提亮。

## 6. 未验证 / 边界

1. **本机 headless 为 SwiftShader 软光栅**：暗区/均值是真实渲染像素统计（可信），但**帧率不代表真机**；本任务不涉及帧率结论。
2. **kit 侧改动的观感**：真实浏览器里的窗洞/窗扇外观未做人工目视（只做了像素统计与几何断言）；洞口新增后，从室内斜视窗位理论上能看到"墙上有洞+窗扇"，未见异常但未逐帧目视。
3. **日景宫灯拉满仍不达标的原因未深挖**：`lampIntensityScale=1.0` 日景（48.72%）与夜景（1.36%）差异明显，除 exposure（1.0 vs 1.18）外可能还与环境的按预设灯位激活策略有关 —— 这属 t2 环境系统范围，我只报了实测差值，未改其代码。
4. **金砖 envMap 的效果未实测**（属环境系统；`interiorBrick` 已有 `envMapIntensity 0.5`，但场景无环境贴图 → 当前无效）。
5. **寝殿夜景也不达标**（40.82%）：说明 C 内景的灯位/陈设组合本身偏暗，即使"夜景已达标"的结论只对金銮殿成立。
